# Round 55 evidence

Deliverable: the audit trail's ordering guarantee is now exercised by the suite.

## What round 54 found, stated plainly

Round 48 added `V50__Signal_Status_Timeline_Order.sql`: a monotonic `seq` column so the status timeline
would not depend on a timestamp that ties. The query orders by `createdAt desc, coalesce(e.seq, 0) desc`.

`coalesce(e.seq, 0)` is the tell. I wrote it to survive a database that has no insertion sequence. It
also hid the real situation: **under the test suite every row had `seq = null`.**

Two reasons, and only the obvious one was on my radar:

- `SignalStatusEntry.seq` was mapped `insertable = false, updatable = false`, so Hibernate never wrote
  to it.
- The column only ever came from the migration. `application-test.yml` sets `ddl-auto: create-drop`, so
  **Hibernate drops whatever Flyway built and recreates every table from the entities** - and the
  recreated column was a plain `bigint` with no default. There was nothing to assign to it.

In production (`ddl-auto: validate` + Flyway) the column exists and V50 works. So the fix was correct for
production and completely unexercised by the suite: the ordering guarantee that matters when a resident
reads an audit trail to judge whether a municipality responded had never been tested.

No test in the repository referenced `seq` at all.

## The test that could not pass before

```java
for (var event : timeline) {
    assertThat(event.getSeq())
        .as("status event %s has no insertion sequence, so the timeline is ordering by "
            + "timestamp alone - the defect V50 exists to prevent", event.getId())
        .isNotNull();
}
```

Before:

```
[status event 00097ee8-... has no insertion sequence, so the timeline is ordering by timestamp alone
 - the defect V50 exists to prevent]
```

It then asserts the sequence is monotonic descending, because present-but-arbitrary would not be the
guarantee either: with `createdAt` alone, two transitions a click apart share a timestamp on H2 and the
database may return them either way round.

### One thing the test had to get right to mean anything

`entityManager.flush(); entityManager.clear();` before reading the timeline back. `seq` is
`insertable = false`, so the database assigns it and the managed objects still in the persistence
context carry `null` for it. Without the clear, the test reads Hibernate's in-memory state and would
have reported a broken database that was working. A green test for the wrong reason is the failure mode
this round has been circling.

## The fix: one line of column definition

Three attempts were needed and the first two are worth recording as dead ends:

- `@GeneratedValue(strategy = IDENTITY)` - Hibernate refuses `@GeneratedValue` off the identifier.
- `@Generated(event = INSERT)` - compiles, but the generated DDL is still a plain `bigint`, so nothing
  is assigned. Adding `@GeneratedColumn` conflicts: it is itself a `@ValueGenerationType`.

What works is repeating the clause V50 already declares:

```java
@Column(
    name = "seq",
    insertable = false,
    updatable = false,
    columnDefinition = "bigint generated by default as identity"
)
private Long seq;
```

`columnDefinition` is emitted verbatim into Hibernate's generated DDL, so the recreated column carries
the identity and the database assigns to it on insert - exactly as the migration does in production.
Same SQL on H2 and PostgreSQL; V50 already proves the clause works on the production engine. And with
`ddl-auto: validate` in production nothing is generated at all, so this cannot affect a deployed schema.

Verified by mutation: removing the `columnDefinition` puts the test back to red with the original
message.

## Audited for the same shape

`insertable = false` across every entity: one occurrence, the one just fixed. No other column in the
codebase depends on DDL that `create-drop` would not reproduce.

## Known limits

- **The migrations themselves are still unexercised.** `create-drop` means every `V*.sql` reaches
  production untested by the suite - not just this column. Fixing that means letting Flyway build the
  test schema, which is a decision about what the integration tests are for rather than a bug: it would
  surface any drift between the 49 migrations and the entities, all at once. Deliberately not attempted
  here.
- **The ordering test relies on H2 storing the identity the same way PostgreSQL does.** The clause is
  shared, but the backfill in V50 (`row_number()` rejected, correlated count used) is exercised only
  where migrations run - which is currently nowhere in the suite.
- `coalesce(e.seq, 0)` is now redundant for rows written after this change, and still the right thing for
  rows written before it. Left in place deliberately.
