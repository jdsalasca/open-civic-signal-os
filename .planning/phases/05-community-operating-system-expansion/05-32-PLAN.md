# Phase 5.32 Plan - Open Civic Data Exports and Scoped API

## Objective

Implement `story:OCS-P1-052` so authorized communities can export civic data in interoperable CSV/JSON formats and issue narrowly scoped external-access tokens with explicit rate limits and audit trails.

## Scope

- add backend-owned community export surfaces for:
  - signals
  - proposals
  - votes
  - decisions
  - trust metrics
- add one lightweight scoped token model for external consumers instead of a full separate auth platform:
  - create token
  - revoke token
  - show scope, status, last-used metadata, and per-hour rate limit
- reuse backend-owned community permissions, dedicated open-data access logging, and rate limiting rather than inventing frontend logic
- support both authenticated in-product export download and scoped token access for JSON/CSV endpoints where appropriate
- add one export-center workflow in the frontend with token guidance and dataset actions
- update OpenAPI, ADR, changelog, backlog, and state so the next canonical story remains explicit after shipping

## Acceptance Criteria

- exports exist for signals, proposals, voting, decisions, and trust metrics
- scope and rate-limit behavior are explicit in the contract and visible in the UI
- privileged exports leave an auditable backend trail
- scoped external access can be issued and revoked without opening unrestricted API access
- backend, contract, frontend, docs, and tests land in one story-scoped change set

## Validation

- `npm run agent:context:check`
- `npm run backlog:current:check`
- `npm run agent:adr:check`
- targeted backend integration tests for export delivery, token scope checks, rate limits, and audit logging
- `mvn -q test` in `apps/api-java` if the environment supports the broader suite
- `npm run docker:dev:up`
- frontend build plus Playwright evidence for the export-center workflow through the Docker runtime

## Minimal Delivery Slice

- add one new community permission scope for managing exports and scoped API access
- add one `CommunityOpenDataToken` persistence model with hashed token storage and explicit dataset scopes
- extend the current export service into community-scoped CSV/JSON dataset builders instead of creating dataset-specific controllers from scratch
- expose one controller surface for token management and one for export consumption
- log export events through a dedicated community open-data access log with dataset and community context
- use the existing `RateLimitService` as the base for token throttling, extending it only enough to support explicit per-key limits
